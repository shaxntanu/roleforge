# 1. What RoleForge Is

RoleForge is an **agentic career compiler**.

It takes a candidate's existing **portfolio codebase / developer portfolio repository** as the primary source of truth, acquires and verifies a target job description, maps job requirements against verifiable candidate evidence, and produces tailored:

- Resume
- CV, when enough information exists
- LaTeX source
- PDF output
- Job-specific application variants
- Evidence / truth audit
- Job fit and gap analysis
- Related job and role recommendations

The central principle is:

> **The candidate's portfolio/codebase is the source of truth for candidate claims.**

> **The job description is the source of truth for job requirements.**

> **Never invent candidate experience, employment, education, achievements, technologies, metrics, responsibilities, or qualifications.**

RoleForge is NOT a generic AI resume writer.

It should behave like a compiler:

```text
Portfolio / Codebase
        ↓
Repository Analysis
        ↓
Candidate Evidence
        ↓
Career Knowledge Base
        ↓
Job Description
        ↓
Requirement Extraction
        ↓
Evidence ↔ Requirement Matching
        ↓
Application Strategy
        ↓
LaTeX Generation
        ↓
Resume / CV
        ↓
Truth + Quality Validation
        ↓
PDF
```

# 5. Job Description Acquisition Priority

Implement the following priority order.

## Primary priority

```text
1. Official job API, if available
2. Official company careers page
3. Job URL provided by the user
4. Permitted/legal web retrieval
5. User-provided job description
6. Online search for verification
```

The source must be recorded.

Example metadata:

```yaml
source:
  type: official_company_page
  url: https://example.com/jobs/123
  retrieved_at: ...
  verified: true
```

When the user provides a job description:

DO NOT silently replace it with a different version found online.

Instead:

```text
User JD
   ↓
Verification
   ├── Match → trusted
   ├── Partial match → discrepancy report
   └── Conflict → flag for user review
```

Example:

```text
⚠ Job description verification

User supplied version:
"Embedded Systems Intern"

Official source:
"Firmware Engineering Intern"

3 requirement differences detected.

The user's supplied JD will remain available as the original source.
```

# 6. Portfolio Is Always the Candidate Source of Truth

RoleForge must extract candidate evidence from:

- source code
- repository structure
- README files
- project descriptions
- package manifests
- configuration
- documentation
- project pages
- GitHub metadata
- releases
- issues
- pull requests
- commit history, when useful

Optionally accept:

- existing resume
- CV
- LinkedIn export
- certifications
- user-provided factual information

But these do NOT override repository evidence automatically.

Every candidate claim should have provenance.

Example:

```yaml
claim:
  text: "Built an ESP32-based IoT weather station"
  evidence:
    - source: projects/zephyr-station/README.md
    - source: src/esp32/
    - source: portfolio/projects.ts
  confidence: direct
```

---

# 7. Evidence Confidence

Use explicit confidence states.

At minimum:

```text
DIRECT
SUPPORTED
INFERRED
WEAKLY_INFERRED
UNSUPPORTED
```

Rules:

```text
DIRECT
→ Explicitly present in source material.

SUPPORTED
→ Supported by multiple pieces of evidence.

INFERRED
→ Reasonable technical inference from evidence.

WEAKLY_INFERRED
→ Possible but insufficiently established.

UNSUPPORTED
→ No evidence.
```

Only sufficiently supported claims may appear in generated application documents.

Never convert:

```text
React → Angular experience
```

or:

```text
ESP32 → FreeRTOS experience
```

or:

```text
Git commits → leadership
```

without actual evidence.

Related skills may be labeled as transferable or adjacent, but must never be represented as direct experience.

# 13. Resume vs CV

Resume and CV should be treated as different document types.

## Resume

Typically:

- concise
- job-specific
- optimized around relevant experience
- generally one page for early-career candidates unless context requires otherwise

## CV

Broader:

- research
- publications
- academic work
- projects
- education
- certifications
- presentations
- broader record

Do NOT automatically generate a CV if the candidate's source material does not justify one.

Return:

```text
CV status:
INSUFFICIENT_INFORMATION

Missing:
- research details
- publications
- academic history
```

when appropriate.

# 14. Project Ranking

Build a relevance-ranking system for portfolio projects.

Conceptually:

```text
Project relevance =
    Requirement overlap
  + Responsibility overlap
  + Skill overlap
  + Evidence strength
  + Recency
  + Role relevance
```

Select the most relevant projects for the specific application.

Do not simply choose projects based on popularity or repository star count.

# 15. Quantification Rules

Metrics must be evidence-backed.

Never invent:

```text
+40% performance
+30% efficiency
10x improvement
```

unless the evidence exists.

When a metric is absent:

Prefer truthful qualitative language.

Example:

Bad:

```text
Improved latency by 35%.
```

when no benchmark exists.

Good:

```text
Optimized rendering and state management for a responsive web interface.
```

Every quantified claim must have traceable evidence.

# 21. Resume Family Concept

Do not create a completely new resume for every single job.

Create reusable resume families:

```text
resume-families/
├── embedded/
├── firmware/
├── frontend/
├── research/
├── iot/
└── ...
```

A job can then use an existing family with minimal tailoring.

Example:

```text
Embedded Resume Family

Company A
→ 95% same

Company B
→ 90% same

Company C
→ 88% same
```

This reduces unnecessary generation while preserving job-specific relevance.
